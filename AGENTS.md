# AGENTS.md

Guidance for humans and AI agents working on this repository.

## What this is

dojo is an AI-guided interview-prep trainer: a CLI (`dojo`) that runs a daily loop of warm-up retrievals → solve → judge → self-report complexity → empirical profiler → AI review → reflection, persisted to SQLite, with FSRS-lite spaced repetition deciding what comes back when. Its defining constraint is the **never-solve rule**: the tutor agent guides, it never solves. Read `README.md` first (the user-facing pitch + guide); design docs live in `docs/`, delivered and planned stages in `roadmap/`, and everything below assumes that split.

## Setup and commands

```bash
make sync                  # uv sync with UV_CACHE_DIR=.uv-cache (sandbox-safe)
make test                  # uv run pytest -q
make seed                  # scripted first-run: dojo setup --user andy --skip-key --no-path
uv run dojo                # bare entry = the daily routine; first run opens the setup wizard
DOJO_AI_BACKEND=mock uv run dojo   # offline demo of the full pipeline
uv run dojo warmup         # due retrievals only
uv run dojo progress       # per-pattern proficiency + cards + score trends
```

Python ≥ 3.13. Deps are managed by uv; add new ones with `uv add`, never by hand-editing the lockfile. **Always route uv through `make` targets or set `UV_CACHE_DIR=$(pwd)/.uv-cache` yourself** — the default uv cache lives outside the workspace and trips sandbox file policies.

## Hard rules

1. **Never-solve is an architectural property, not a prompt detail.** Reference implementations (oracles in `judge/registry.py`) must never enter tutor context. The tutor prompt (`tutor/prompts.py`) receives only: statement, student code, tier, hint history. If a change adds a new file with solution code, keep it outside anything the tutor imports or reads. **One deliberate narrowing (v0.8):** learning mode's teacher may show *topic-canonical* code — its context is the topic name + conversation only, never a problem statement (never-solve protects solves, not knowledge). The narrowing is pinned by `test_teacher_prompt_carries_topic_only` and does not extend to the tutor, reviewer, or curator.
2. **Copyright — private use.** dojo serves two PhD students' private practice. Statements, visible tests, and other data may draw on public sources (LeetCode, books) and live in the bank as normal; the repo stays private — never publish the bank or its data. The seed corpus is the users' own writing where it exists.
3. **Secrets.** `DEEPSEEK_API_KEY` lives in the environment or a gitignored `.env`. Never log it, never put it in prompts, tests, or fixtures.
4. **User data is real.** `data/dojo.db` and `workbench/` are personal state. Don't delete or reset them as a side effect; DB migrations are additive only (`ALTER TABLE ... ADD COLUMN` or new tables).
5. **Tests are offline and deterministic.** No network calls in tests; always use `MockBackend`. Measurement tests target coarse outcomes (class, slope range), not exact timings.
6. **Prompt changes require test updates.** The leak-check behavior, tier gating, and mock canned responses are asserted in `tests/test_tutor.py` and `tests/test_flow.py`. Change a prompt → update the mock to mirror it and adjust the assertions in the same commit.
7. **Respect the honesty contract.** The profiler reports evidence ("consistent with O(n) at tested scales", R², confidence), never proofs. Don't add heuristics that convert low-confidence fits into confident classes.

## Conventions

- **Judge protocol:** `runner.py` writes `solution.py` + `cases.json` + a harness into a temp dir and executes it with a timeout. Case dicts: `{"args": [...], "expected": any, "label": str}` plus optional verdict tags — `"compare": "sorted"` (deep-sorted equality for any-order outputs), `"compare": "approx:1e-4"` / `"rounded:n"` (float tolerance), `"predicate": name` (a `@checker` in the registry validates `(module, got, args)`), or `{"ops": [...], "expected": [...]}` (class problems: instantiate `function_name`, replay the method sequence). Default is strict JSON equality with `sort_keys` — don't "fix" it to approximate float equality without updating README and tests. **Channel hygiene (v0.10.1):** the harness runs user code inside `isolated()` (stdout → stderr) — a `print` in a solution once corrupted the result JSON and crashed dojo; and per-case handlers catch `BaseException`, so `sys.exit()` is a case error, not a harness death. The profiler's measurement subprocess swaps stdout the same way.
- **Registries:** per-slug decorators in `judge/registry.py`: `@oracle(slug)` (correctness reference), `@judge_case(slug)` (small random cases with expected values; may return a third extras dict carrying the same verdict tags), `@profiler_input(slug)` (worst-case-shaped inputs of size n — never early-exit inputs; see the random-bracket lesson in docs/grading.md), and `@checker(name)` (predicate verdicts). Generators must clamp n into the problem's constraints (the caller sends 0..12).
- **Measurement protocol:** one timed call per subprocess; GC disabled around the call; tracemalloc started after module import; median across repeats. The subprocess boundary exists to contain hangs — don't replace it with in-process timing. **Space points are classified on every-second point** (`fit.staircase_safe_points`): container allocations are a power-of-two staircase that aliases a linear structure as exponent 2 at exact doublings — don't remove the subsample without porting `tests/test_profiler.py`.
- **Curating a new problem:** add `function_name` + `visible_tests` + a `signature` (string for one function, `{"functions": {...}}` for multi-function problems, `{"methods": {...}}` for class problems) to `data/problem_overrides.json`, and a generator/oracle pair in `judge/registry.py` (a `@checker` for predicate problems, a `@profiler_input` unless measurement is meaningless). The startup auto-reseed keeps the DB fresh (an upsert, so it never deletes rows attempts reference). The judge's verdict modes mean prompts can honestly say "any order": tag those cases `"compare": "sorted"` and emit canonical form from the oracle. Trees are nested lists `[value, left, right]` (`None` = missing child / empty tree). `tests/test_registry.py` pins the contract — update it when the curated set changes. `dojo curate` automates the recipe via the curator agent (a separate agent from the tutor — its oracle output must never enter tutor context; `tests/test_never_solve.py` pins that boundary) and applies only when the verification gate passes, rolling back otherwise.
- **Static analysis (v0.4):** runs automatically on every successful submit (`static.analyze`): radon cyclomatic complexity per function + ruff findings, stored on the attempt row (`static_analysis` JSON) and fed to the reviewer prompt as evidence. Complexity > 10 (McCabe convention) is a flag, never a failure; tool hiccups degrade into `notes`. Add new deps with `uv add` — never hand-edit the lockfile.
- **Fetcher (v0.3):** `dojo fetch <title-slug>` pulls a LeetCode problem (GraphQL), converts content HTML to plain text (`fetcher/htmltext.py`, stdlib only), maps topic tags → pattern via `patterns.py` (unmapped tags fail loudly — never a silent wrong bucket), parses the python3 starter snippet into `function_name` + `signature` hints (annotation normalization: `List[int]` → `list[int]`, `Optional[X]` → `X | None`; empty snippet bodies get padded), lands the seed file via `fetcher.land()`, then auto-curates through the curator + verification gate. The HTTP transport is an injected callable — tests pin the contract against canned GraphQL fixtures and must never hit the network.
- **Tutor protocol (v0.6):** one `hint` command, two AI-classified modes — "ladder" (stuck: respond at the tier, advance; only ultra-short zero-information messages force tier 0) and "discussion" (exploring: answer directly, no tier). `ask_tutor` calls `chat_json` with a `{"kind", "tier", "text"}` schema; every response passes the leak audit, and one still rated >= 3 after retries is **discarded, never shown**. History entries record `kind`. The post-solve `discuss` command uses `DISCUSSION_SYSTEM` (boundary lifts after solving; the prompt carries the submitted code via `build_discussion_prompt`, so the model grounds on what actually ran) and persists the transcript. The reviewer returns a normalized rubric (bare-int dimensions wrapped by `reviewer.normalize_review`; scores clamped to 1-5). **JSON resilience (v0.9.1):** `backend.parse_json_content` tolerates fenced and prose-wrapped objects; `chat_json` caps output at 4096 tokens (a truncated mid-object response is exactly the "non-JSON" failure real sessions saw); and the reviewer's retry goes through the plain `chat` path (temperature 0.3) instead of repeating the identical temperature-0 request — change any prompt or parsing step → update the mock and tests in the same commit (rule 6). MockBackend keys canned branches on system-prompt substrings: the discussion branch matches "post-solve" (DISCUSSION_SYSTEM never contains the literal word "discussion" — the branch silently died once and tests passed against the wrong fallback); keep teacher/discussion branch words disjoint from the prompts.
- **Report command (v0.7):** `dojo report [slug]` (and in-session `report`) audits curation via `curator.audit_curation`: fresh curator run → cross-check fresh oracle vs live oracle on generated cases → audit agent hunts prompt-vs-judge contract violations. `--fix` re-curates (`apply(overwrite=True)` — new registry block wins at import; rollback restores original files, overrides, registrations). Report JSON lands in gitignored `data/curation/`.
- **Learning mode (v0.8):** a third agent, the teacher, for topic education (`dojo learn [TOPIC]`; picker without a topic, `difflib` did-you-mean on typos; in-session `learn` parks the attempt and teaches the pattern — warm-ups reject `learn`: leaving a warm-up is a lapse, not a pause). `run_learn` persists the transcript to `learn_sessions` after **every exchange** (crash-safe), `completed` marks graceful ends. The teacher's context is topic + conversation only (rule 1's documented narrowing); it may show topic-canonical code, and is instructed to say so when unsure — there is no oracle for pedagogy. `TEACHER_SYSTEM` must avoid the words "tutor" and "discussion" — MockBackend keys its canned branches on system-prompt substrings (`teacher` branch sits in `chat`, after `discussion`); change the prompt → update the mock + `tests/test_never_solve.py` in the same commit (rule 6). `practice` inside learn mode hands off to the easiest unsolved curated problem in the pattern (`scheduler.pick_practice_problem`); accepted handoffs return `{"practice": slug}`, and `_cmd_day`/`_cmd_learn` loop solve sessions while the outcome is `"practice"` — always the same slug (an in-session learn retries the parked problem). The proactive offer fires only for scheduler picks from unstudied patterns (`db.unstudied`: no learn session AND no attempts) and is a fork, never a gate. `studied_patterns` (learn sessions ∪ attempts) is the one shared notion feeding the offer and the `dojo progress` markers.
- **Terminal ergonomics:** interactive prompts use `dojo/terminal.make_prompt` (prompt_toolkit when on a TTY — arrow keys, wrapped-line editing, history; `console.input` otherwise, which tests exercise). `make_prompt` accepts a `default` for prefilled answers (TTY-only sugar; the non-TTY path ignores it — tests assert the plain path). **The submit questions (v0.9.1):** time/space/reflection render via `flow.ask_question` — blank line, bold-cyan question, answer typed on its own line under a dim `❯`. **Virtual-text prompts (v0.10.1):** `make_prompt(..., hint=...)` renders the command list as virtual text — right-aligned ON the input line via prompt_toolkit's `rprompt` (the bottom toolbar proved unreliable in some terminals and rendered nothing; the input line is the region every terminal draws for sure). Keep hints short (they share the input line). Non-TTYs print the hint above the prompt (which tests exercise), and any TTY-path exception now logs a `prompt_fallback` event to the debug log before degrading — prompt failures are never silent again. The `hint` and `discuss` commands are gone: any non-command input is a question, pre- and post-solve alike (a leading "hint " prefix is still stripped for muscle memory). `patch_console` wraps the rich Console in run_day/run_learn so prints between prompts route through prompt_toolkit.patch_stdout — the fullscreen prompt's repaint can otherwise visually truncate output (the reported "hist" cut-offs; the debug log proved those responses were complete, so the loss was terminal-side). The two complexity answers pass a **double-check gate** (Enter continues; `time`/`space` re-asks that one question, prefilled on a TTY) — they remain two separate questions feeding separate analyses; only the gate is shared. **Polish re-claims (v0.9.3):** `_polish` re-collects both claims through the same `_ask_complexity_claims` helper with the previous answers as prefilled defaults, and persists them — comparing a new measurement against stale claims produced spurious flags. Rich tables come from `dojo/ui.table` (vertical padding between rows). Tutor/discussion responses cap at 2048 tokens; `de_markdown` handles bullets, headers, blockquotes, horizontal rules, and dunder bolds — keep it updated as models invent new artifacts.
- **Scheduler:** the FSRS-lite model lives entirely in `scheduler.py` with documented constants (FACTOR/DECAY/S0/D0/TARGET_R). Grades are 1-4 (Anki convention). Don't swap in a scheduler library without porting `tests/test_scheduler.py`; same-day reviews legitimately yield no stability growth (R ≈ 1). **The progression gate (v0.10):** `pick_new_problem` walks the roadmap groups in order under a hard prereq gate (`patterns.PREREQS`, a chain over the verified group order — the mirror carries the order, not the site's DAG edges) and serves the earliest unsolved ladder problem of the first eligible pattern; ladder matching runs on `problems.lc_number` (bank rows are only ladder-visible when curated), dojo's own problems are the fallback (weakest pattern first). `pick_practice_problem` respects ladder order within its pattern. `scheduler.ladder_state` exposes (solved lc, curated bank lc) to the roadmap view.
- **Warm-up semantics:** `run_warmups` forces a fresh template (re-solve from scratch), creates an attempt with `kind='warmup'`, skips reflection (the recall grade replaces it), and quits record a lapse. Workbench state is per (slug, kind) and lasts exactly one session: it is retired (deleted) on submit and on quit, so every `dojo day` invocation gets a fresh attempt row — a warm-up never reuses a solve session's tier/hints, and repeat sessions never overwrite earlier attempt rows. Quitting persists code + hints to the abandoned attempt row. **Every new session writes a blank template over the workbench file** (solves and warm-ups alike); previous solutions live on attempt rows and are recoverable via `dojo history` / `dojo show <id>`.
- **AI prose rendering (v0.10.3):** the prompts now *require* Markdown (short `##` headings, plain-dash lists, `**bold**` terms, fenced code blocks — the tutor still never emits a full solution, and only at tier 5 may it fence code). `dojo/render.py` is the one display path: `render_ai(console, title, text, border_style=...)` prints a bordered Panel whose title is the context and whose content is rich Markdown (code fences syntax-highlighted, `CODE_THEME`), and `md_plain(text)` exports deterministic plain text for table cells and pipes. Border styles follow the pre-v0.10.3 conventions (blue for tutor/teacher, green for post-solve discussion, cyan for reflection feedback). Transcripts/reviews store the model's markdown **as-is**; `dojo show` renders history through the same path. `de_markdown` in `tutor/tutor.py` is retired from display duty (kept + tested as the legacy plain-text fallback); underscores are never stripped (identifiers like `two_sum`) — pin render behavior with `tests/test_render.py`.
- **Debug logging (v0.9.2):** every live AI exchange is appended to the gitignored `data/logs/dojo.log` (JSONL: system prompt, user prompt, the raw response *before* parsing, latency, and transport errors). Only `DeepSeekBackend` logs — MockBackend never writes, so tests stay offline; tests that exercise the logger monkeypatch `debuglog.LOG_PATH` onto tmp paths and never touch the real log. `dojo/version.py` holds `MAJOR_VERSION`: the marker check per write clears the log when the version bumps (the size-explosion guard — bump it when shipping a major stage). Never log the API key.
- **Complexity table colors (v0.9.2):** `_show_complexity_table` renders cells as literal `rich.text.Text` — rich Tables strip markup in cells, so `[red]...[/red]` strings would silently render plain. Any cell participating in a mismatch is red; a fully agreeing axis is green; the note line explains. Cell values are literal text (never markup-parsed), so raw user strings from the polish path are safe. Tests render through a real `Console(no_color=False)` capture — the harness sets `NO_COLOR=1`, and `str(table)` is just an object repr.
- **Workbench & VSCode (v0.10.1):** the workbench lives OUTSIDE the repo at `~/.local/share/dojo/workbench` (`DOJO_WORKBENCH_DIR` overrides; `XDG_DATA_HOME` respected) — editor/debugger tooling (ipykernel etc.) never collides with git. The tracked `.vscode/settings.json` pins `python.defaultInterpreterPath` to the repo venv, and `.vscode/launch.json` carries the "dojo: debug the active workbench file" debugpy config. Tests monkeypatch WORKBENCH_DIR onto tmp paths everywhere — never the real location.
- **Updater (v0.10.1):** `update_dojo` (in `updater.py`, injectable runner — offline tests) fast-forwards the repo (`--ff-only`, or `--force` = reset --hard) and runs `uv sync` only when the pull changed files; failures degrade into notes, never break the run. `auto_update()` runs on every CLI entry except `setup`/`update` (opt out with `DOJO_NO_AUTO_UPDATE=1` — the agent/dev escape hatch) and prints only when something changed. Never auto-update from tests — they call `_cmd_*` directly, and `main()` help paths return before the hook.
- **Editor launching:** all `$EDITOR` behavior lives in `editor.py` — GUI editors detach via `Popen(start_new_session=True)`, terminal editors go through tmux/osascript, unknown editors block. Don't call subprocess directly from `flow.py`; tests cover the pure classification helpers only, never process spawning.
- **SQLite:** `db.py` owns schema and connection. Keep `sqlite3.Row` access by name. JSON columns go through `dumps_json`/`loads_json`.
- **CLI:** argparse subcommands in `cli.py`; each returns an exit code. Bare `dojo` runs the daily routine (argv normalization: a first non-flag, non-subcommand argument is a slug; `dojo day` is the alias). **One computer, one user** — no `--user` flags: the active user resolves from gitignored `data/dojo.conf` → the DB's sole user; zero users = first run → the setup wizard (`dojo/setup.py`) runs, then the original command continues (non-TTY prints guidance instead of prompting). Every entry (except `setup`) runs `bank.ensure_seeded` first — the bank always mirrors `problems/` (additive upsert; at the CLI layer, never in `db.connect()`). `dojo user [name]` switches the active user (numbered picker without a name; an unknown name errors — never a silent typo'd account); `dojo learn [TOPIC]` is the learning-mode entry (USER_COMMANDS member; the `_choose` picker is shared with `dojo user`). **Help surface (v0.9):** `dojo help` = `dojo -h` = `dojo --help` is intercepted in `main` (any argv starting with those) and prints the hand-written `HELP_TEXT` — never argparse's listing. `roadmap` (v0.10) is a visible command: `_roadmap_rows` builds the pure row data (ladder counts, complete/next-up/locked-by), `_cmd_roadmap` renders it. Power tools (`day`, `warmup`, `check`, `show`, `curate`, `report`) and `profile` (a hidden alias of `_cmd_history`) stay dispatchable but never appear in the guide; each still documents itself via `dojo <cmd> --help`. Don't use argparse's `help=SUPPRESS` — Python 3.13 prints `==SUPPRESS==` literals. **Setup key detection (v0.9):** `run_wizard(detect_env_key=True)` resolves env → dotenv → prompt; a detected key skips the prompt, an env-sourced one is persisted to the dotenv. `--skip-key` passes `detect_env_key=False` so scripted installs (`make seed`) never write a key. Interactive flows read from `console.input` — tests use the `FakeConsole` fixture (its `actions` hook simulates editing the workbench mid-session). `history` (list attempts, newest first) and `show <id>` (full attempt detail, `--code` for code only) render rows fetched by `db.list_attempts` / `db.get_attempt`.

## Definition of done

- `uv run pytest` passes; new behavior has tests.
- The never-solve boundary is unchanged or deliberately narrowed with rationale in the PR description.
- User-visible changes update `README.md` (guide) and the matching `docs/` file (technical); new stage work lands in `roadmap/`.
