# v0.9 — onboarding: minimal help, new-user README, key detection

Status: ✅ delivered.

## Goals

1. **Radically simplified help.** `dojo help` = `dojo -h` = `dojo --help` (intercepted in `main` before argparse) prints a hand-written guide: bare `dojo` usage + the seven everyday commands (`learn`, `list`, `progress`, `history`, `fetch`, `user`, `setup`). Power tools stay dispatchable but never listed: `day`, `warmup`, `check`, `show`, `curate`, `report` — and `profile`, which became a hidden alias of `history` (audit proposal 4: one review surface). Each still documents itself via `dojo <cmd> --help`.
2. **New-user README.** Rewritten around the actual first-run path: prereqs, `git clone` → `uv run dojo` → wizard → plain `dojo`. Explicit that you run from a checkout; the wizard is described step by step; the mock-backend escape hatch is up front.
3. **Setup key detection.** `run_wizard` resolves the key as environment → dotenv → prompt. A detected key skips the prompt (and an env-sourced key is persisted to the dotenv so every shell sees it); `--skip-key` disables detection too, so scripted installs (`make seed`) never write a key.
4. **Ergonomic pre-wrapper start.** The answer to "how do I start before `dojo` exists" is documented as the only command: `uv run dojo` (uv builds the project env automatically — no `make` needed). The wizard's closing line now points at `uv run dojo` when the PATH install is declined.

## Lessons

- argparse's `help=argparse.SUPPRESS` prints `==SUPPRESS==` literals on Python 3.13 — hiding lives in the interception, not the parser.
- The env-detection tests pin `detect_env_key=False` on the prompt paths: a keyed ambient environment must never make them flaky (determinism rule 5).

## v0.9.1 — live-session fixes (first beta feedback)

1. **Reviewer "non-JSON" failures (2 of 3 submits).** Three hardening layers: `backend.parse_json_content` tolerates the shapes the API actually emits (markdown fences, prose-wrapped objects); `chat_json` caps output at 4096 tokens (a truncated mid-object response is exactly this failure); the reviewer's retry now goes through the plain `chat` path (temperature 0.3, no json_object mode) instead of repeating the identical temperature-0 request, which would reproduce the same failure. Not reproduced live — the agent shell has no API key — so the fix is defensive coverage of every plausible cause; watch the next few sessions.
2. **Editable complexity answers.** The two complexity questions stay separate (separate analyses), but a **double-check gate** now sits between them and the measurement: a compact summary of both answers, Enter to continue, `time`/`space` re-asks that one question — prefilled on a TTY via `make_prompt(default=…)`.
3. **Breathing room.** Time/space/reflection render via `flow.ask_question`: blank line, bold-cyan question on its own line, answer typed beneath a dim `❯`.
4. **Complexity table:** the Flag column is gone; an **R² column** shows at a glance whether a surprising measured class is a measurement artifact (the evidence-not-verdict note stays, now pointing at low R² as the noise tell).

## v0.9.2 — debug logging + colored complexity table

1. **Debug logging backend.** Every live AI exchange is appended to the gitignored `data/logs/dojo.log` as JSONL — system prompt, user prompt, the raw response *before* parsing, latency, and transport errors — so a buggy session can be debugged without copy-pasting the terminal. Only `DeepSeekBackend` logs (MockBackend never writes; tests stay offline). The size-explosion guard: `dojo/version.py` holds `MAJOR_VERSION`, and the per-write marker check wipes the log when the version bumps — bump it when shipping the next major stage.
2. **Colored complexity table.** Any cell participating in a mismatch renders red; a fully agreeing axis renders green. Learned the hard way that rich Tables strip markup in cells — cells are literal `rich.text.Text`, never `[red]…[/red]` strings, and the harness's `NO_COLOR=1` means table tests render through a real `Console(no_color=False)` capture (`str(table)` is just an object repr).

## v0.9.3 — polish re-claims complexity

`polish` used to measure the *edited* code but compare against the *original* claims — spurious flags. It now re-collects both claims through the shared `_ask_complexity_claims` helper (double-check gate included) with the previous answers as prefilled defaults, uses them for the table and the optional re-review, and persists them on the attempt row. An unchanged polish costs three Enters; a rewritten algorithm gets honest flags again.
