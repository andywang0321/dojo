# v0.10 — systemic pattern progression (a NeetCode-shaped roadmap)

Status: planned; design forks pending (see "Open decisions").

## The diagnosis

dojo's pattern taxonomy is fine-grained but **flat and thin**: 14 patterns with no ordering between them, no ordering within them, and a bank whose coverage collapses after the first three techniques. Measured against the canonical NeetCode 150 list (the de-facto standard ladder):

| NeetCode group | dojo coverage |
|---|---|
| Arrays & Hashing | 8/8 ✓ |
| Two Pointers | 5/5 ✓ |
| Stack | 7/7 ✓ |
| Sliding Window | 0/6 |
| Binary Search | 0/7 |
| Linked List | 0/11 |
| Trees | 2/15 |
| Tries | 0/3 (no such pattern) |
| Heap / Priority Queue | 1/7 |
| Backtracking | 0/9 |
| Graphs | 0/13 |
| Advanced Graphs | 0/6 (folded into graph) |
| 1-D DP | 0/12 |
| 2-D DP | 0/11 (folded into dynamic_programming) |
| Greedy | 1/8 |
| Intervals | 0/6 (no such pattern) |
| Math & Geometry | 0/8 |
| Bit Manipulation | 0/7 |

**24/150 covered** (plus ~8 problems outside the 150). The scheduler's "weakest pattern first" then makes it worse: it happily serves whatever exists, with no notion that a pattern has prerequisites or that a pattern's problems form a ladder. The result feels random — correctly.

## What the NeetCode tree teaches (design lessons, not just a list)

1. **A progression graph, not a flat taxonomy.** The roadmap is 18 technique groups in prerequisite order (arrays → two pointers → sliding window → stack → binary search → linked list → trees → tries → heap → backtracking → graphs → advanced graphs → 1-D DP → 2-D DP → greedy → intervals → math & geometry → bit manipulation). Sliding window before two pointers would be pedagogically wrong; the order *is* the system.
2. **Each group is a difficulty ladder, and each problem teaches one new trick.** Arrays & Hashing: contains_duplicate (set) → valid_anagram (counting) → two_sum (complement map) → group_anagrams (canonical key) → top_k (bucket/frequency) → product_except_self (prefix/suffix) → valid_sudoku (indexing) → longest_consecutive (set + streaks). Every next problem is the *least novel* unsolved problem — minimal marginal difficulty.
3. **Coverage follows a power law.** Trees 15, graphs 13+6, DP 12+11 — the core techniques get the most reps; support techniques (tries 3, intervals 6, bit 7) get enough to establish the pattern.
4. **dojo's missing dimension is *order*, and its missing content is *breadth*.** The taxonomy needs prereq edges + per-pattern problem sequences; the bank needs the ~126 missing free problems (which dojo's existing `fetch` + curator pipeline can produce — the machinery already exists).

## The data question: API and scraping

- **NeetCode has no official public API.** The site is a Next.js app with unversioned internal endpoints; relying on them is fragile and against the ToS. Scraping neetcode.io is both unnecessary and disallowed by its robots/ToS.
- **The roadmap *list* needs no scraping.** The free NeetCode 150 structure is public knowledge and cleanly mirrored in community repos (e.g. [lufftw/neetcode](https://github.com/lufftw/neetcode) ships it as a `roadmaps/neetcode_150.toml`: 18 ordered groups × ordered LeetCode numbers — verified against the live site). Vendoring that list into the repo (with provenance noted) is consistent with the private-use policy.
- **The problem *content* already has a legal-for-private-use path**: NeetCode displays LeetCode's own statements, and dojo already fetches those through its injected GraphQL client (`dojo fetch <slug>`) with the HTML→text converter and auto-curation + verification gate. So the pipeline is: **vendored roadmap list → `dojo fetch` per slug → curator → judge registrations**, entirely through dojo's existing machinery. Zero scraping of neetcode.io.

## The proposal

1. **Progression graph in the taxonomy** (`patterns.py` + a new data file): prerequisite edges between patterns (derived from the NeetCode group order) and a canonical *ordered problem sequence* per pattern (vendored `data/roadmap.toml`, mapping NeetCode group → ordered LeetCode numbers, with a `dojo`-side mapping slug ↔ LC number stored on problem rows).
2. **Scheduler respects the graph.** `pick_new_problem` becomes: walk patterns in topological order; the next problem is the earliest unsolved problem in the first unsatisfied pattern whose prerequisites are all satisfied. Stability/weakest-first becomes the tiebreak *within* the eligible frontier. Explicit `dojo <slug>` stays exempt (the deliberate-choice precedent from the proactive offer).
3. **`dojo roadmap` view.** The tree rendered in the terminal with solved/unsolved/next-up markers, per-pattern progress, and prereq state — the "third way" surface for the new system.
4. **Content acquisition in batches.** Machinery first, then complete each group's ladder top-down from Arrays & Hashing (already 8/8) through the 150, one batch per milestone, each problem through the existing fetch + dual-oracle curation + verification gate (the gate already makes bulk import safe). Batch size is a session's worth of curation runs; `MAJOR_VERSION` bumps and log clearing ride the ship of v0.10.0.
5. **Migrations stay additive.** New patterns (tries, intervals, and optionally the 1-D/2-D DP and advanced-graphs splits) are new rows/tags; existing attempt rows keep their pattern values — but see Open decisions on renaming.

## Open decisions (need your call)

1. **Adopt vs adapt.** Do we re-bucket the bank onto NeetCode's exact 18 groups, or keep dojo's 14-pattern taxonomy and add only the systemic bits (prereq edges + per-pattern ladders + the missing patterns `tries` and `intervals`, optionally splitting `dynamic_programming` → 1-D/2-D and `graph` → graphs/advanced)?
2. **Scheduler strictness.** Hard gate (scheduler never serves a problem whose pattern has unsatisfied prerequisites) vs soft deprioritization (prereq-unsatisfied patterns sort last)?
3. **Content pace.** Machinery + one complete group per milestone (recommended), vs a bulk import run of all ~126 problems now, vs machinery only with no new problems yet?
4. **`dojo roadmap` in v0.10?** Yes (recommended — the tree is the point) or defer to a later stage?
5. (Defaulted, flag if you disagree) The vendored list lives in `data/roadmap.toml` with a provenance header crediting the NeetCode 150 structure; dojo keeps its own hand-written problems (correlation, array_intersection, …) in their patterns outside the canonical ladder.

## Build order sketch (after the decisions)

1. `data/roadmap.toml` vendored + `patterns.py` prereq edges + tests.
2. `problems` schema: optional `lc_number` column + `sequence` per pattern (additive migration) + bank importer reads them.
3. Scheduler: topologically ordered `pick_new_problem` + prereq gating per decision 2 + tests.
4. `dojo roadmap` view + tests.
5. First content batch (per decision 3) through `dojo fetch` + curation; verification-gate reports as evidence.
6. Docs (README progression section, architecture), MAJOR_VERSION bump, ship.
