# v0.5 — setup wizard, single-user ergonomics, the bare `dojo` entry

Status: planned. Design settled (see "Settled decisions"); implementation follows the order in "Build order".

## Goals

1. First run of any command opens a guided setup wizard (API key, user name, one-time init, PATH install). `dojo init` disappears.
2. One computer = one user: every `--user` flag is removed; `dojo user` switches the rare exception, git-branch style.
3. Bare `dojo` = the daily routine, with a status line before and a "next up" footer after — information, not a menu. `dojo day` stays as an alias.
4. The bank re-seeds automatically at every startup, so `problems/` always mirrors the DB and no one ever wonders where problems come from.
5. `dojo` goes on PATH during setup via a live wrapper (git pull updates flow through automatically).
6. `dojo learn` (future stage) gets its no-argument picker contract noted now, so the pattern is consistent.

## Settled decisions

- **Menu vs. routine:** bare `dojo` drops straight into the daily routine. A status line ("2 warm-ups due · next up: Valid Palindrome") provides trajectory without decisions; the session-end footer suggests tomorrow's work. `dojo --help` is the menu; build a dedicated menu only if a concrete need appears (YAGNI).
- **Auto-reseed on startup:** yes, including the nuance that read-only commands (`dojo list`) upsert newly added problem files. It's additive-only and idempotent (~50 ms at bank scale), and it runs at the CLI entry layer — never in `db.connect()` (bank imports db, so the reverse would be circular).
- **PATH mechanism:** a wrapper script `~/.local/bin/dojo` that execs `uv run --project <repo> dojo "$@"` — always live code, no stale snapshot after `git pull`. Shell rc is edited only with explicit consent, showing the exact line first.
- **User switcher:** `dojo user` (no argument) lists users as a numbered picker; `dojo user <name>` switches like `git switch`. An unknown name errors — never silently creates a typo'd user.

## Design

### A. Active-user configuration

- New gitignored file `data/dojo.conf` (JSON): `{"user": "andy"}`.
- Resolution order at runtime: conf user → sole DB user → (wizard creates one on first run). If the conf names a user missing from the DB, error with a hint — never auto-create a typo.
- Backward compatible: an existing install with a sole user (e.g. `andy`) keeps working without the conf file.
- Shared machines: `dojo user` lists, pick a number, conf is rewritten.

### B. The setup wizard (`dojo setup`)

- Runs automatically on the first command that needs the DB/user; `dojo setup` exists to re-run (change key, reinstall the PATH wrapper, add a user).
- Steps: welcome → API key (detect env/`.env`; else masked `getpass` prompt writing `.env`, with a mock-mode skip) → user name (default from `$USER` / git identity) → one-time init (create DB, seed bank, register user, backfill cards) with a plain-language summary → PATH install offer (write wrapper, `chmod +x`, PATH-append consent) → mock smoke test ("You're set. Next: `dojo`").
- Scriptable flags for CI/Makefile: `--user NAME`, `--skip-key`, `--no-path`.
- Pure logic lives in `dojo/setup.py` (testable against tmp paths); the CLI shell is thin.

### C. Bare `dojo` = the daily routine

- `main()` normalizes argv: no args → `day` with no slug; a first arg that isn't a known subcommand or flag → treated as a slug (`dojo valid_parentheses` ≡ `dojo day valid_parentheses`). The normalizer is a pure function with its own tests.
- `dojo day [slug] [--skip-warmup] [--open]` remains, as the documented alias.
- Status line: due-card count + the scheduler's pick, printed before the session. Footer: due cards tomorrow + the strongest-pattern trend line, after the session.

### D. `dojo user`

- No args → numbered picker over `SELECT name FROM users`; pick → rewrite conf.
- `<name>` → switch if the user exists, else error ("unknown user 'x' — `dojo user` to list, `dojo setup` to add").
- All `--user` flags removed from `day`/`warmup`/`profile`/`history`/`progress`/`list`; internal resolution becomes `_active_user(conn)` (conf → sole user → error-with-wizard-trigger).

### E. `dojo learn` contract (noted, not built here)

`dojo learn [topic]`; no topic → numbered picker over the pattern taxonomy (same picker component as `dojo user`). Full learning-mode design stays in `roadmap/next.md`.

### F. `init` removal

- `p_init`/`_cmd_init` deleted; the wizard covers first-run and `dojo setup` covers re-runs; auto-reseed covers bank updates.
- Makefile `seed` target becomes `$(UV) run dojo setup --user andy --skip-key --no-path` (scripted).

## Build order (test-driven)

1. `data/dojo.conf` + `_active_user` + remove `--user` flags + `dojo user` with picker (rewrite `tests/test_cli.py` for the new resolution).
2. Auto-reseed at the CLI entry (`ensure_seeded`), tests for upsert + no-op.
3. Bare `dojo` entry: argv normalization, status line, session-end footer; `day` alias.
4. The wizard: `dojo/setup.py` (key → `.env`, user default, summary, PATH wrapper + rc consent), auto-trigger on first run; scripted flags; Makefile update.
5. Delete `init`; update README (`dojo` first-run story), `docs/architecture.md` + `docs/development.md`, AGENTS references; full suite green; commit.
