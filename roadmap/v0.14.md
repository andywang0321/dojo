# v0.14 — curricula: JAX first, Rust second

*Planned 2026-09-19. Source: the coupling inventory and transfer analysis in the
[v0.12 audit](../docs/audit-v0.12.md) §4, plus the persistence constraints in its
§S3.4/S5.5.*

dojo's formula — spaced repetition + a never-solve tutor + machine-verified
grading — is not about LeetCode. It is about *practice with feedback*, and the
one thing every version of that needs is a unit of practice that can be
**graded without a human**. So the question this stage answers is not "how do we
support another language" but:

> What is the smallest honest definition of a *curriculum* that the existing
> engine can serve unchanged, and what does each candidate curriculum actually
> need beyond it?

The two candidates are deliberately far apart. **JAX is the cheap half** — it is
Python, so the judge harness, the static layer, the curator's Python trust root
and the workbench file all keep working. **Rust is the expensive half** — the
artifact becomes a crate, the judge becomes a build+test pipeline, the modal
error is *rejection* rather than a wrong answer, and the interesting units have
no cost curve at all. If a single abstraction covers both, it is the right one;
if it only covers JAX, we should know that after one increment rather than after
a rewrite.

## What transfers, and what does not

| Concern | LeetCode today | JAX | Rust |
|---|---|---|---|
| Unit taxonomy | `patterns.PATTERNS`, 18 slugs (`patterns.py:13-32`) | topics: jit, pytrees, autodiff, vmap, scan, rng, dtype, … | ownership, borrowing, lifetimes, traits, generics, Result, iterators, closures, smart pointers, concurrency, async |
| Progression | a **chain** (`PREREQS`, `patterns.py:61-63`) | mostly a chain, with branches | a **DAG** (traits/generics/async/Result are converging branches) |
| Item identity | `slug` + `lc_number` (`db.py:25,36`) | slug; no external id | slug; no external id |
| Artifact | one `.py` file (`state.py:37`) | one `.py` file — unchanged | a **crate**: `Cargo.toml` + `src/lib.rs` + `tests/` |
| Correctness | call a function, compare the return | call a function, compare the return **and** check transformation properties | `cargo test`; compile success is itself a graded outcome |
| The characteristic failure | wrong answer, wrong complexity | tracer error, silent re-trace, host→device round trip, dtype/shape surprise — *all of which still return the right number* | **does not compile**: borrow/lifetime/trait diagnostics |
| Static layer | radon + ruff (`static.py`) | ruff (right tool, blind to what matters) | `cargo clippy --message-format=json` (strictly better than radon+ruff) |
| Measurement | paired growth vs a reference (`probe.py`) | compile time, blocked step time, device memory, shape scaling — **not one class in one variable** | none for ownership units; allocation counts where it matters |
| Reference / oracle | curator-generated Python, gated against a brute-force oracle | same pipeline, with `jax` in the exec namespace | **no AI path** — the curator cannot write Rust; references are authored and gated by building them |
| Cards | `(user, pattern)` (`db.py:67-80`) | `(user, jax:topic)` — works | `(user, rust:concept)` — works, but the retrievable skill is a *rule* ("read a signature, infer the borrow"), not a problem |
| Never-solve | the tutor must not name the algorithm | odd: the tutorial line and the answer are often the same line (`jax.vmap(f)`) | **more** valuable: the compiler is a second teacher, and a tutor that refuses to write the `&mut` is exactly right |
| Toolchain | dojo's own venv, via the shebang | needs `jax` — a per-curriculum venv | needs `cargo`/`rustc` — dojo cannot provision it |

Three consequences worth stating plainly:

1. **A curriculum is not a language flag.** It is a bundle of decisions:
   taxonomy + progression, artifact shape, runner, verdict vocabulary,
   measurement policy, and the agent's rubric. Anything less leaks the LeetCode
   shape into every new curriculum (which is exactly what the 28-row coupling
   inventory describes).
2. **Rust may not be Dojo-shaped.** If the interesting exercise is "make this
   compile, then make this not compile", the judge's job becomes
   *diagnostic-shaped* rather than value-shaped, and `visible_tests` + hidden
   generators + a paired growth probe have little to say. Validate that with
   content before building the runner (Increment 3, step 0).
3. **JAX breaks the measurement story, not the grading story.** A JAX item can
   be graded correctly with today's harness, but "is this fast" means something
   else entirely — and if we measure it wrongly we violate the honesty contract
   that v0.11/v0.12 paid for.

## The abstraction

```
curricula/
  leetcode/curriculum.toml     # the 18 groups, the ladders (today's roadmap.toml)
  jax/curriculum.toml          # topics + items + judge/measure policy
  rust/curriculum.toml
  <slug>/items/<item>.py|.toml # item content: statement, tests, reference
```

A `curriculum.toml`:

```toml
[meta]
slug = "jax"
title = "JAX for ML engineers"
language = "python"
artifact = "file"                 # file | crate
runner = "python-cases"           # python-cases | cargo-test
measure = "jax-shape"             # scale-pair | jax-shape | none
difficulty_vocab = ["intro", "core", "advanced"]   # free text, CHECK-free

[[unit]]
slug = "jit"
title = "JIT and tracing"
prereqs = []                      # explicit edges; a DAG, not a chain
items = ["trace_a_function", "avoid_python_side_effects"]

[[unit]]
slug = "vmap"
prereqs = ["jit"]
items = ["batch_a_naive_loop", "vmappable_loss"]
```

The five concepts, and the seam each needs:

1. **Curriculum** — mostly exists: `data/roadmap.toml` + `roadmap.load_roadmap`
   are already a curriculum file hardcoded to one instance. Needs: drop the
   mandatory integer key (`roadmap.py:42`), add language/runner/measure, allow
   explicit prereq edges.
2. **Unit** (today's "pattern") — exists as module constants
   (`patterns.PATTERNS`/`PREREQS`) and as the FSRS card key. Must become data;
   `patterns.py` demotes to "the LeetCode curriculum's units + the LeetCode
   tag→unit map used by the fetcher".
3. **Item** (today's "problem") — the field set exists (`db.problems` +
   `data/problem_overrides.json`); the *encodings* are the leak: identity via
   `slug` + `lc_number`, difficulty via a CHECK over
   `Easy|Medium|Hard` (`db.py:27`, which `ALTER TABLE` cannot relax),
   statement-as-Python-docstring, template-as-Python-source.
4. **Artifact** — **no seam, and the first thing to build**:
   `WorkbenchState.code_path` returns one `Path` ending `.py` (`state.py:37`) and
   six downstream call sites treat it as a Python file
   (`flow.py:330,338,477,657,671,790`). A crate is a directory, so `Path` is the
   wrong type the moment Rust exists. v0.13 already introduces the view layer
   (`session/workbench.py`); v0.14 adds `Artifact(language, root, entry, tests)`.
5. **Runner** — the *interface* is right and language-agnostic:
   `run_cases(...) -> JudgeReport` with `CaseResult` (`runner.py:137-153`). The
   body is 100% Python (`HARNESS`, `sys.executable`, `cases.json`). Needs a
   runner spec (`cmd`, `env`, `timeout`, `parse`) and a second implementation.
6. **Scheduler policy** — FSRS itself transfers unchanged (pure math over
   `(user, unit)`, `scheduler.py:68-238`); the *walk* is hardcoded to the
   LeetCode roadmap (`scheduler.py:288-400`, `_roadmap_groups` is
   `lru_cache(maxsize=1)`) and the *key* is a bare unit slug, which would let
   LeetCode "stack" and Rust "stack" share one card.

### Schema, additively

AGENTS.md rule 4 (additive migrations only) constrains the design in a useful
way: instead of rebuilding `problems` to get `UNIQUE(curriculum, slug)` and a
relaxed difficulty CHECK, **namespace the keys**:

- `problems` gains `curriculum TEXT NOT NULL DEFAULT 'leetcode'`, `item_ref TEXT`,
  `language TEXT`, `unit TEXT` (the `pattern` column keeps its name and meaning —
  a unit slug).
- Non-LeetCode curricula use qualified keys: slug `jax:softmax_stable`, unit
  `jax:jit`, or the row's `curriculum` column plus a `curriculum`-qualified
  unique index (`CREATE UNIQUE INDEX IF NOT EXISTS … ON problems(curriculum, slug)`,
  which *is* additive). The v0.10 lesson applies: one authority for a key, or
  the bank drifts (audit S5.1 — 18 problems currently exist twice because the
  file stem was the identity).
- New `curriculum_units(id, curriculum, slug, title, position, prereqs JSON)` —
  the taxonomy becomes data; `patterns.PATTERNS` seeds the LeetCode rows.
- `pattern_cards` gains `curriculum`; the card key becomes
  `(user, curriculum-qualified unit)`.
- **No nullable `attempts.problem_id`.** A "read this doc, then answer three
  questions" item is still an item row (`judge = "none"`, a checklist instead of
  cases), so the FK stays NOT NULL and pre-v0.11 history semantics are untouched.
- `items` for a curriculum with no judge verdict record `status = "recalled"`
  and no code — the learner model gains a row without changing shape.

## Increment 1 — the platform seam, with JAX riding the Python path (~1 stage)

**Goal.** A second curriculum exists end to end and nothing downstream changes,
because JAX items are Python files graded by the existing judge.

- `curricula/<slug>/curriculum.toml` loader (`roadmap.load_curriculum`),
  keeping `load_roadmap` as the LeetCode adapter so no caller breaks.
- `problems`: `curriculum`, `item_ref`, `language`, `unit` (additive).
- `bank.ensure_seeded` imports every curriculum's items; `--curriculum` on
  `day` / `warmup` / `list` / `roadmap` / `progress` / `learn`; `dojo curricula`
  lists what is installed with toolchain health.
- The active curriculum resolves from conf (`dojo curriculum jax`), defaulting to
  `leetcode`; the workbench state path and slug keys become
  curriculum-qualified.
- Scheduler: `pick_new_problem` / `ladder_state` / `pick_practice_problem` /
  `_prereqs_satisfied` take a curriculum and walk *its* unit order with *its*
  prereq edges; `_roadmap_groups` loses its process-wide `lru_cache(maxsize=1)`.
- Runtime: a per-curriculum venv (`dojo curriculum setup jax` → `uv pip install
  jax` into `curricula/jax/.venv`, consent-gated, version recorded), and the
  judge's runner spec points `sys.executable` at it instead of dojo's own.

**Content.** Author 8–12 JAX items by hand (the first unit: tracing/JIT
semantics), each with a statement, 3–5 visible cases, a canonical reference, and
a property tag. Hand-authoring is deliberate: the curator is good at
LeetCode-shaped problems and unproven on transformation semantics.

**Tests.** A JAX item solves end to end under the mock backend; a LeetCode
session is byte-identical to v0.13 (same pick, same card key, same workbench
path); curriculum-scoped identity (the same slug in two curricula is two rows,
two workbenches, two cards); `dojo roadmap --curriculum jax` renders the DAG
(including a unit with two prereqs, which the chain format cannot express).

**Risk.** The ladder key is load-bearing (AGENTS.md: "ladder matching runs on
`problems.lc_number`; bank rows are only ladder-visible when curated"), and
`tests/test_scheduler.py` pins the gate. A sloppy item-key mapping serves the
wrong problem or locks a unit forever. Mitigation: the LeetCode path keeps
`lc_number` as its item key and every refactor is guarded by "the LeetCode
roadmap output is unchanged" as a golden test.

## Increment 2 — measuring JAX honestly (~1 stage)

**Goal.** A JAX item can say something true about performance, or explicitly
nothing.

What the current probe would report, and why each line is wrong:

| Today's mechanism | What it does to JAX |
|---|---|
| untimed warm-up then a timed bare call (`probe.py:112-128`) | the warm-up absorbs XLA compilation, so **compile time — the first thing a JAX learner must internalize — is timed by nothing**; and without `block_until_ready()` the timed call returns when the *dispatcher* queues work |
| `tracemalloc` for the space axis (`probe.py:137-140`) | counts host-heap Python allocations; **device memory (HBM) is structurally invisible** |
| one `n`, doubled | the wrong axis for shape/dtype/batch scaling |
| ratio vs a Python reference | fine *within* a runtime; meaningless across interpreter-vs-compiled |

The replacement is a **measurement mode**, not a parameterization: `measure =
"jax-shape"` selects a per-item policy that reports (i) first-call compile time in
its own region, (ii) steady-state step time after `block_until_ready()` at each
shape on the item's shape ladder, (iii) device memory where the backend exposes
it, with an explicit "not measurable on CPU" otherwise, and (iv) the paired
comparison against a *naive but correct* reference (a Python loop / an
un-jitted version) so the verdict stays relative — rule 7 still forbids a bare
number.

The verdict vocabulary gains three outcomes that are the actual pedagogy:
`RETRACED` (the function re-traces on every call — the classic `jit` misuse),
`HOST_ROUNDTRIP` (a per-call device→host transfer inside a hot loop), and
`PYTHON_LOOP_IN_TRACE` (a Python-level loop that should be `scan`/`fori_loop`).
Honest note: the *mechanism* for detecting re-tracing is an open question with
two candidates — `jax.monitoring` counters, or comparing lowered HLO identity
across calls. Choose it in the stage doc, pin it on a synthetic case (a jitted
function called twice with identical shapes must read as not-re-traced), and do
**not** ship a verdict whose mechanism is a heuristic dressed as a fact.

**Tests.** Synthetic shape-series for every new verdict (never wall-clock —
rule 5, and audit S5.6 is what happens when this rule slips); a re-tracing
implementation reads `RETRACED`; a correct `jit`+`block_until_ready` step reads
`matches`; a CPU-only machine reports device memory as "not measurable" rather
than 0; the reviewer prompt receives the new verdicts with the same
confidence wording as today (`_measurement_note`).

**Risk.** This is the stage where dojo could start *lying* about performance in a
new dialect. The mitigation is the existing discipline: verdicts are relational,
"unresolved" is a first-class outcome, and a measurement is only ever evidence
for the reviewer, never a score.

## Increment 3 — Rust (~2 stages, and it may want a different product)

**Step 0, before any code: author five Rust items by hand** — one ownership, one
borrow, one lifetime, one `Result`/`?`, one compile-fail exercise — in the format
below, and run them by hand with `cargo test`. If the interesting content does not
fit that format, stop and redesign the judge around diagnostics rather than
cases. This is the cheapest possible falsification of the whole increment.

**Spec.**

- **Artifact.** `Artifact(language="rust", root=<crate dir>, entry="src/lib.rs",
  tests="tests/")`. The template renderer writes `Cargo.toml` (name, edition,
  and the item's dependencies), `src/lib.rs` (statement as `//!` module docs + the
  signature with `todo!()`), and `tests/visible.rs` (the item's visible tests as
  real `#[test]`s). The student can `cargo test` the crate in their own terminal,
  which is the Rust-native equivalent of `dojo check` — and pedagogically
  better, because the failure message is the teaching.
- **Runner.** A `cargo-test` runner: `cargo test --message-format=json` in the
  workbench crate, parsed into `CaseResult`s (one per `#[test]`), with
  `status ∈ {correct, tests_failed, compile_failed, timed_out}`. Diagnostics are
  structured (error code, span, message) and **not** truncated to 500 characters
  — for Rust the compiler message *is* the feedback, and truncating it defeats
  the curriculum (audit C8/S2.x).
- **Verdict modes.** `{"compile_fail": true, "error_code": "E0502"}` — pass iff
  rustc rejects the code, optionally with the expected code. This is the standard
  unit of the Rust Book and rustlings, and it is a genuinely new axis: the
  existing comparators are all *value*-shaped.
- **Static layer.** `cargo clippy --message-format=json` replaces radon+ruff for
  Rust items; `StaticReport` gains a language-neutral findings list.
- **Never-solve, amended.** A pasted borrow-checker suggestion *is* the fix, so
  the tutor's context gets the diagnostic (error code + span + message) but the
  prompt forbids restating the suggestion as code, and the reviewer may quote it.
  This is a deliberate, documented narrowing of the narrow side of the boundary —
  pin it with a test, the way the v0.8 teacher narrowing is pinned.
- **Oracle and reference.** The curator cannot write Rust. Items ship an authored
  reference (`src/reference.rs`) and a fixture table (JSON inputs/expected
  outputs generated by that reference at authoring time), and a new
  `dojo curriculum verify rust` builds the reference and replays the fixtures —
  the same role the curator's verification gate plays for LeetCode, with a human
  as the author instead of a model. Item provenance records the `rustc` version,
  because diagnostics differ between toolchains.
- **Measurement.** `measure = "none"` for ownership/borrow/lifetime/type-system
  units — and say so in the UI ("no cost curve for this unit: the failure mode
  is rejection, not slowness") rather than showing an empty column. Algorithmic
  Rust items may use the paired probe; that grades the language the student
  already knew, which is fine but is not the reason for the curriculum.
- **IDE.** `editor.ensure_ide_config` grows a Rust variant: rust-analyzer
  `linkedProjects`, a CodeLLDB launch config, `cargo test` as the run profile.
  No shebang analogue exists, so the "which interpreter" problem disappears.
- **Toolchain.** `dojo curriculum setup rust` probes for `cargo`/`rustc`, prints
  the `rustup` command if absent (never auto-installs), and fails the curriculum
  with a clear message rather than a traceback.

**Tests.** Runner: compile error → `compile_failed` with code preserved; test
failure → `tests_failed` with the per-test name; `compile_fail` case passes on a
borrow error and fails on a compiling solution; clippy findings become evidence
and never a verdict; the reference gate refuses a fixture mismatch; the tutor
prompt carries diagnostics but no code; the workbench crate is byte-identical
after a re-render except the student's `src/lib.rs`.

**Risk (highest in this document).** Rust is where dojo stops being one product:
the artifact is a tree, the judge is a pipeline, the interesting verdict is
"rejected", and the static layer is the compiler. Each of those is a real change
to a core abstraction. The two-stage split (artifact+runner, then content+polish)
and Step 0 exist to keep that risk visible.

## What this stage deliberately does not do

- **No third-party plugin API.** Curricula are in-repo data; a public plugin
  interface is premature and would freeze the wrong seams (the 28-row coupling
  inventory is the evidence for which seams are real).
- **No automatic toolchain provisioning.** Installs happen only with explicit
  consent (`dojo curriculum setup`), and only into a curriculum-local venv or
  the user's existing rustup.
- **No cross-curriculum cards.** A card belongs to `(user, curriculum, unit)`.
  Sharing "stack" between LeetCode and Rust would make the schedule lie.
- **No web UI, no TUI.** The CLI loop is the product until it is not.
- **No retrofitting of the LeetCode content gap.** 126 of 150 ladder problems
  remain uncurated (audit S5.3/S2.13); the curriculum work must not be an excuse
  to leave the ladder permanently stuck at 24 rungs. Land Increment 1 first, then
  batch-curate — the tooling for that (`dojo fetch --all`, `dojo reference --all`,
  `dojo report --fix`) already exists and should be run once the identity
  problem (audit S5.1) is fixed.
- **No new spaced-repetition model.** FSRS-4.5 works; the *card unit* changes
  (per-item cards are worth revisiting — audit S3.4), but the equations do not.

## Definition of done

- `dojo --curriculum jax` runs a full session (warm-up → solve → judge → measure
  → review → reflect → card) on a hand-authored JAX item, with a verdict that
  names a transformation property and never a cost class the ratio cannot
  support.
- The LeetCode experience is unchanged: same picks, same workbench path, same
  card keys — proven by a golden test over `dojo roadmap --table` output.
- `dojo curriculum verify rust` builds every Rust item's reference and replays its
  fixtures; a `compile_fail` item fails when its exercise is solved.
- `docs/curricula.md` exists and states, per curriculum, what is measured, what
  is graded, what the tutor may say, and what is explicitly *not* claimed.
- README gains a "Dojo for other curricula" section that is honest about the
  asymmetry: JAX is a drill, Rust is a course, and the two share an engine
  because they share a unit: something you can practise, that a machine can
  check, and that fades without repetition.
