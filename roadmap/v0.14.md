# v0.14 — the curricula rebuild

*Planned 2026-09-25 on branch `v0.14-curricula`. Source: the design discussion of
2026-09-25 (its five agreed decisions are recorded in §7), the coupling inventory in
[the v0.12 audit](../docs/audit-v0.12.md) §4, and the persistence constraints in its
§S3.4/S5.5.*

dojo's first three years produced one product with one curriculum baked into it: the
engine and the NeetCode 150 were the same repository, the same vocabulary, and the
same import graph (`patterns.py` alone is imported by seven engine modules;
`judge/registry.py` is 1,579 lines of LeetCode content living inside the grader).
That was the right way to discover what the product is. It is the wrong way to build
the second curriculum.

This phase is the split. It ships **no new curriculum** and **no new student-facing
capability**: it turns the current product into an engine plus a curriculum that
happens to be NeetCode 150, keeps the daily loop exactly as it is, and makes the
next curriculum a separate repository instead of a fork of this one.

---

## 1. What a curriculum is

A curriculum is a **local, versioned bundle of practice** that declares six things
and nothing else:

1. **Topics** — the learnable units of the subject, their order and their
   prerequisites (a graph, not a chain).
2. **Items** — the things you practise: one artifact, one statement, an optional
   external id, a difficulty in the curriculum's own vocabulary.
3. **Assessment** — how a submission is checked, and what kind of evidence that
   produces: executable (cases against an oracle), measured (a cost/shape/behaviour
   comparison against a paired reference), judged (an AI rubric), or self-reported.
4. **Measurement policy** — what to measure for this item, on which axis, against
   which baseline; or an explicit "not measurable here".
5. **Warm-up policy** — what recall means for this item (re-solve it, re-derive it,
   re-justify a choice) and how the recall grade is collected.
6. **Display vocabulary** — the words the student sees for the structure above
   (`Ladder`, `Pattern`, `Module`, `Difficulty`), because the engine's neutral nouns
   are not a curriculum's nouns.

Plus the bookkeeping that makes it safe to depend on: an id, a version, the engine
versions it is compatible with, declared dependencies, a provenance record, and an
alias map for renames. The full format is [docs/curricula.md](../docs/curricula.md);
it is **v1 and unstable** until two real curricula use it.

The engine, correspondingly, is everything that is true regardless of the subject:
the schedule, the session, the artifact and its views, the judge harness, the
measurement framework, the AI roles, the evidence record, enrollment, storage,
display, and the CLI.

## 2. What moves, and what stays

| concern | today | after |
|---|---|---|
| topic taxonomy | `patterns.PATTERNS` (168 lines, imported by 7 engine modules) | the NeetCode curriculum's manifest |
| progression | `PREREQS` chain + `roadmap.toml` + `lc_number` ladder matching | the manifest's topic graph; the engine walks it |
| item identity | file stem, plus `lc_number` | `(curriculum, item_id)` + optional `external_id` |
| statements, tests | `problems/**/*.py` docstrings (161 files) | the curriculum's `items/` |
| curated metadata | `data/problem_overrides.json` (31 entries) | item metadata in the manifest |
| oracles, generators, references, checkers | `judge/registry.py` (1,579 lines) | the curriculum's `assessment/` (quarantined) |
| source intake | `fetcher/` (LeetCode GraphQL) | a curriculum tool |
| curator taxonomy text | baked into `CURATOR_SYSTEM` | supplied by the curriculum at call time |
| the ladder *view* | `cli._roadmap_*` | the engine's generic outline view + curriculum display words |
| FSRS, session loop, workbench, judge harness, measurement framework, AI roles/guards/budgets, evidence, enrollment, DB, CLI, debug log, version | — | **stay** |

## 3. Increments

### Increment 0 — the documentation rewrite (this commit)

The branch's first act is to re-describe the product from the new perspective, so
that the code is written against the docs rather than the other way round. Ship:
this file, `roadmap/README.md`, `roadmap/history.md`, a rewritten `README.md` and
`AGENTS.md` (including the two-branch discipline), and `docs/{architecture,
curricula,grading,retention,authoring,development}.md`. The pre-split phase records
(v0.1–v0.13) are retired from this branch — they describe a design that will not
exist here — and condensed into `roadmap/history.md` with a pointer to `main` for
the full text. No code.

### Increment A — the seam, behaviour-preserving

**Goal.** The engine speaks curriculum-neutral nouns, loads a curriculum from a
directory, and behaves *identically* for the student on the NeetCode 150.

- `dojo/curriculum/`: the manifest dataclasses, validation, the loader, the two
  namespaces, and the generic decorators assessment code registers with.
- `tests/fixtures/curriculum-demo/`: the spec-by-example curriculum — two topics,
  four items, one executable, one measured, one judged, one that declares "not
  measurable", plus a rename alias. It is the loader's test double and the skeleton
  `dojo curriculum new` copies.
- **Schema, additively**: `curricula`, `curriculum_topics`, `enrollments`, and the
  item columns (`curriculum`, `item_id`, `external_id`, `evidence_tier`), plus the
  partial unique index `(curriculum, external_id) WHERE external_id IS NOT NULL`.
  The three renames (`problems`→`items`, `problem_id`→`item_id`, `pattern`→`topic`)
  follow the protocol in §4.
- `evidence.py`: the tiers and provenance fields exist and are recorded; the
  *behaviour* that consumes them (gating, audit, conservative seeding) is phase 15.
- The NeetCode 150 is expressed as a curriculum **inside this repo for now** (a
  directory that increment B moves out), so A can prove behaviour-preservation
  before anything leaves.
- Neutral vocabulary throughout the engine: `topic`, `item`, `outline`; the
  curriculum supplies `Ladder`/`Pattern` for display.

**DoD.** Every existing test passes; a *golden capture* taken from `main` at the
merge point (a session's picks, the outline render, the workbench path, the card
keys) is reproduced byte-for-byte; `bare dojo` with no curriculum enrolled behaves
like today's NeetCode default because the NeetCode curriculum is auto-enrolled on
first run.

**Risk.** This is where a refactor silently changes behaviour. The mitigation is
that the goldens are captured from `main` *after* the last merge, and that the
curriculum directory in this increment is a straight transcription of today's
`patterns.py` + `roadmap.toml` + corpus + registry.

### Increment B — NeetCode 150 leaves the repository; enrollment arrives

**Goal.** This repository contains no content, and a student enrolls a curriculum
from a link.

- Create the private `dojo-curriculum-neetcode-150` repository: the manifest (18
  topics, 150 items, prerequisites), the corpus and statements, the item metadata
  (today's overrides), the assessment modules (today's registry content, split per
  topic), its tools (`fetch`), and its own README/AGENTS explaining its conventions.
- `dojo enroll <git-url|path|id>` installs into `config.CURRICULA_DIR` with a
  `.dojo-source.json` (URL, commit, installed-at), validates the manifest, imports
  the catalog, and enrolls it. `dojo curricula` lists installed + enrolled state;
  `dojo unenroll <id>` pauses without touching history; `dojo curriculum
  new|validate|verify|update` are the power tools (create from the fixture, validate
  a manifest, verify a curriculum's own gates, update from its source).
- Remove from this repo: `problems/`, `data/roadmap.toml`,
  `data/problem_overrides.json`, `patterns.py`, `fetcher/`, the registry content.
- The setup wizard ends with an offer to enroll a starter curriculum; a fresh
  install with nothing enrolled explains the one command that changes that, rather
  than pretending to have work to do.
- **The picker** (agreed design): only *session* commands ask — `dojo`,
  `dojo <item>`, `dojo warmup`, `dojo learn`. The question is asked once and
  remembered (`What would you like to study today? 1. NeetCode 150  2. JAX
  [Enter = 2]`); a bare Enter accepts the default; a unique item id resolves without
  asking; `--curriculum <id>` stays as the scripting escape hatch. **Reporting
  commands stay global** (`history`, `progress`, `list`, `outline`) with an optional
  filter, and **the due queue is global** — a due card is due — labelled per
  curriculum and filterable with `dojo warmup --curriculum`.
- The `personal` curriculum: created on first run, enrolled by default, local only,
  never fetched, and the destination `dojo curate` writes into unless told
  otherwise. It is where the students' own problems live (today: 7 rows, 1 card, 6
  attempts).

**DoD.** A fresh clone of this repo has no content; `dojo enroll <path-or-url>` of
the NeetCode curriculum then `dojo` reproduces today's daily loop exactly; the
engine's test suite runs against the fixture curriculum alone (no network, no
NeetCode checkout); the real corpus is reproducible from its repository.

### Phase 15 — the evidence model, then JAX

Not in this phase, but designed here so the format can carry it:

- **Evidence model** (docs/grading.md is the spec): tiers and disclosure in the
  display, the *gating* rule (a judgment that gates needs an independent audit
  pass), "submitted, unjudged" when the AI is unreachable, and conservative seeding
  for weak evidence.
- **JAX**, as the first curriculum written against the format and the proof it
  generalizes: hand-authored items (the curator is unproven on transformation
  semantics), its own measurement suite (first-call compile time in its own region,
  steady-state step time after `block_until_ready()`, device memory or an explicit
  "not measurable on CPU", re-trace detection), and its verdict vocabulary
  (`RETRACED`, `HOST_ROUNDTRIP`, `PYTHON_LOOP_IN_TRACE`). **Spike before API**: the
  mechanism for re-trace detection is an open question with two candidates
  (`jax.monitoring` counters vs lowered-HLO identity); choose it with a throwaway
  experiment, and never ship a verdict whose mechanism is a heuristic dressed as a
  fact.

### Phase 16 — AI curriculum generation (the fourth term)

The capability that makes a curriculum cheap enough to exist for anything you want
to learn: point dojo at a source you trust (a problem set, a library's docs, a
syllabus), and have it propose a topic graph, author items, gate them, and hand you
a candidate curriculum to review. It is late in the order for a reason — you cannot
generate well what you have not authored by hand once, and JAX is that reference.
A read-only spike (propose an outline from a JAX docs page, no format commitment)
is cheap enough to run during phase 15.

## 4. The migration (the riskiest step)

The live database is a student's real history: 37 attempts, 15 cards, 1 revision,
learn sessions, and the NeetCode bank. It also keeps growing while this branch is
open. So the migration is **rule-based, idempotent and re-runnable**, and its
acceptance test runs against a **fresh copy of the live database at merge time** —
never a snapshot taken today.

**Rules, in order:**

1. Every row with a ladder `lc_number` → the `neetcode-150` curriculum, matched to
   its item by external id; every other row → `personal`. The *rule* is the
   migration; no hardcoded slug list.
2. The four known twin pairs (`maximum-subarray`/`sum_largest_contiguous_subarray`
   LC 53, `product-of-array-except-self`/`products_of_array_except_self` LC 238,
   `diameter-of-binary-tree`/`binary_tree_diameter` LC 543,
   `k-closest-points-to-origin`/`k_closest_points` LC 973) are folded into the
   curated row, and the untagged twin is deleted (no attempts, no cards,
   verified) — *and* any further pair the rule finds at merge time is folded the
   same way and reported, not silently merged.
3. The schema renames happen under protocol: `--dry-run` first, a mandatory backup
   of `data/dojo.db` before the real run, and the whole thing exercised by a test
   that copies the live DB, migrates it, and asserts:
   - **the 15 cards reproduce bit-for-bit** from `rebuild_item_cards` (the
     experiment the user already ran by hand), so due dates and stabilities survive
     the identity change;
   - every attempt is readable (`dojo show <id>`) with its statement intact;
   - no attempt or card is orphaned, and no `(curriculum, external_id)` pair
     collides;
   - a migrated DB equals a fresh one column-for-column (the existing reconcile
     invariant), with the legacy names absent.
4. Rollback is the branch, not the migration: `main` is untouched, the backup is
   the escape hatch, and nothing merges until the acceptance test passes on the
   current live copy.

## 5. What this phase deliberately does not do

- **No new curriculum.** JAX is phase 15; the format is proven by the fixture and by
  transcribing NeetCode, and generalized only where those two need it.
- **No Rust, and no artifact generalization.** Tabled deliberately: the crate case
  would force the artifact to be a tree and the runner to be a pipeline, and every
  planned curriculum is a single Python file. The seams it would need are recorded
  as gaps in `docs/architecture.md`, not built.
- **No plugin API beyond the format.** A curriculum declares content, policies and
  tools; it cannot add AI roles, CLI nouns, or scheduler behaviour. The format is
  v1-unstable, not a public contract with a deprecation policy.
- **No automatic toolchain provisioning.** A curriculum declares its extra
  dependencies; installing them is explicit and consent-gated.
- **No cross-curriculum cards.** A card belongs to `(user, curriculum, item)`; the
  same topic name in two curricula is two memories.
- **No new retention model.** FSRS-4.5 stays; only the card key and the evidence
  disclosure change.
- **No excuse to stop curating.** 126 of the 150 NeetCode ladder problems remain
  uncurated on `main`; that work continues there, independently of this branch.

## 6. Risks

| risk | why it is real | mitigation |
|---|---|---|
| The extraction changes student-visible behaviour | 7 engine modules import the taxonomy; the ladder key is load-bearing | goldens captured from `main` at merge time; the NeetCode curriculum is a transcription before it is a rewrite |
| The migration damages real history | renames + identity change, on a database that keeps growing | rule-based + idempotent, dry-run, backup, replay-based card assertion, tested against a live copy |
| Never-solve breaks silently | curriculum code contains references and oracles, and is external | structural two namespaces, assessment loaded lazily and only in a bounded subprocess, import-graph test per curriculum |
| The format freezes the wrong seams | one implementation proves nothing | v1-unstable until NeetCode + JAX both use it; the fixture is the spec |
| Two parallel branches drift | `main` stays live and keeps shipping fixes | merge `main` in regularly, never rebase shared history, and re-run the acceptance test against the current live DB before merging back |
| Scope creep into JAX/generation | both are more interesting than refactoring | phase 15/16 boundaries are explicit; the only permitted taste of them in phase 14 is a read-only spike |

## 7. Decisions taken (2026-09-25)

1. **Phasing** — phase 14 is increments 0/A/B; the evidence model and JAX follow.
2. **Shipping** — curricula live in their own repositories (published at the same
   level as dojo, enrolled by URL), installed under `CURRICULA_DIR`; the engine
   repository ships none.
3. **Picker** — ask once and remember, Enter accepts; reporting commands stay
   global; the due queue stays global and labelled.
4. **Personal problems** — a default-enrolled local `personal` curriculum.
5. **Judged evidence** — advisory for scheduling; self-report drives the grade; the
   tier is displayed; gating judgments need an audit pass (phase 15).

**Open, to decide at the phase boundary:** the major-epoch bump. The proposal is
`1.14.0` + `git tag v1.14.0` on the merge commit — the engine's identity changes
here, and the version scheme's third component counts commits on a branch anyway
(rule 10), so the two branches showing different counts off `v0.13.0` is expected.
The alternative is to stay `0.x` until phase 15.

## 8. Definition of done

- A fresh clone with no curriculum enrolled explains itself and can enroll one in a
  single command; with the NeetCode curriculum enrolled, the daily loop is
  indistinguishable from `main` — proven by goldens captured after the last merge.
- No LeetCode content, statement, oracle, taxonomy or ladder policy remains in this
  repository (`grep`-able claim, checked by a test that fails if `problems/`,
  `patterns.py` or a LeetCode slug reappears under `src/`).
- The live-database acceptance test passes against a copy taken at merge time: 15
  cards reproduce, 37 attempts readable, no orphaned rows, no duplicate external ids.
- `docs/` describes the engine and never a body of content; the NeetCode curriculum
  repository carries its own conventions.
- The never-solve import-graph test passes for every installed curriculum.
- Merged to `main`, with the version bumped and tagged in the same commit.
