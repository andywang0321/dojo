# v0.13 — session continuity, the workbench file, and providers

*Planned 2026-09-19. Sources: the four reported defects and two feature ideas in
the [v0.12 audit](../docs/audit-v0.12.md) §3, plus the trust findings in its §2
that this stage's code paths would otherwise inherit.*

Five changes, one theme: **the session should behave like a session.** Today the
solve loop and the post-solve loop are separate `while True`s with different
command tables, the attempt row keeps only the newest version of the code, the
AI is handed dojo's own scaffolding as if the student wrote it, and the backend
is one hardcoded provider. Each is small; together they are the difference
between a tool you use daily and a tool you fight.

Deliberately **not** in this stage: fuzzing with shrinking (deferred from v0.12;
it moves to [next.md](next.md) — it is not on the path to a second curriculum),
and the curriculum work itself ([v0.14](v0.14.md)).

## Decisions taken

| Question | Decision | Why |
|---|---|---|
| Where does solution history live? | New `attempt_revisions` table; `attempts.code` stays the head | a JSON blob on the row can't be diffed or joined, and the head keeps every existing query working |
| One loop or two? | **One loop**, `phase` (solving/post_solve) × `agent` (tutor/discussion) as state | two loops is the direct cause of the missing `check`/`open`; a phase table makes "add a command" safe |
| What does `polish` mean? | Take me back to **solving**, with the **discussion** agent answering | the user's reading: polishing is editing, and the boundary is already lifted |
| Is the workbench file the artifact the AI sees? | No — a `WorkbenchFile` view layer: raw file for the judge, **stripped student view** for every AI and for `static` | structural fix for the shebang/docstring noise; a prompt patch cannot fix the hallucinated-lint class |
| Runnable entry point: `__main__` block or a separate runner file? | **`__main__` block**, sentinel-fenced and strippable | works with the existing `${file}`/`$ZED_FILE` configs in every editor; the clutter objection disappears once the AI and `dojo show` see the stripped view |
| Providers | A provider table + `DOJO_PROVIDER`, roles on the backend protocol | also retires MockBackend's prompt-substring routing (next.md #10) |

## Status — Stages 0, A, B, C and D shipped (2026-09-19)

The trust subset, attempt revisions, the phase loop and the workbench view layer
are in `main`; 396 tests pass offline. What actually landed, with the extra
defects the work surfaced:

**Stage 0 (trust).** The leak audit fails closed (non-dict / missing / string /
`None` / **bool** ratings all mean *unknown*, and unknown is not clean; one audit
retry, then the hint is discarded with a message that names the auditor rather
than blaming the answer). The judge captures **file descriptor 1** as well as
`sys.stdout`, reads the last parseable line, bounds both streams, kills the
child's whole process group on timeout, sets address-space/file-size/CPU limits
in the harness, refuses an empty case list, never raises, and reports a case that
raised as `status="error"`. `dojo/proc.py` is the shared bounded runner
(`run_capped`, `killpg`, `apply_child_limits`) and `run_cases(..., python=…)` is
the runner seam for v0.14. Every AI call site runs behind `dojo/guard.py`, so a
backend outage degrades instead of ending the session. `dojo report --fix` can no
longer delete a problem row that attempts reference. The warm-up grade is one
transaction and cannot be applied twice. `dojo curate`'s pattern enum is generated
from the taxonomy that validation enforces. `static.analyze` cannot raise, lints
the student view, and keeps its ruff cache out of the repo. Templates are
validated before they are written. The trend table counts solves, not warm-up
re-solves. Backfill counts the cards it created and seeds them from the solve's
hint count.

**Stage A (revisions).** `attempt_revisions` is additive; every write of the head
row appends the version that produced it, in the same transaction, and attaches
that version's own claims, measurement, static analysis and review. `dojo show
<id> --revisions` lists them, `--rev N` reads one, `--diff [A [B]]` shows what
changed, and `--clean` renders the AI's view of the code. The head still holds
the raw artifact, so every existing query and `dojo show --code` keep working.

**Stage B (one loop).** `phase ∈ {solving, post_solve}` lives in the workbench
state (crash-safe), `agent ∈ {tutor, discussion}` is sticky once a solve is
graded. `polish` **returns to solving** with the discussion agent answering; a
second `submit` re-grades, appends a revision, asks before paying for another
review, and returns to post-solve. Post-solve, a solving-mode command is answered
with a pointer ("`check` is a solving-mode command — `polish` takes you back")
instead of being sent to the model as a question; solving-side, `polish`/`done`
get the mirror-image pointer. `quit` before a submit still records nothing; after
one it ends the session and keeps the attempt. `_post_solve_loop` and `_polish`
are gone.

**Stage C (the workbench file).** `session/workbench.py` owns the template, the
sentinel-fenced `if __name__ == "__main__"` block built from the problem's own
visible tests, and `student_view()` — the projection every AI reader and
`static.analyze` now consume. The block runs under the IDE's Run/F5 (verified for
function, property-checked and class/ops problems) and is never executed by the
grader or the probe, which load the module under another name. A statement that
would not compile is refused loudly (`TemplateError`) instead of being written
out.

**Follow-up (2026-09-21) — warm-up cards are per problem.** A live report ("no
warm-up for days") traced to two things: the footer called a rolling 24 hours
"tomorrow" (fixed: `scheduler.due_phrase`/`due_summary`/`due_hint`), and the
*pattern* card was hiding real debt — 14 solved problems, 4 ever recalled, 10
never. Rebuilding per-problem state from the attempt log gave 14 cards, with the
recalled four at S = 29/36/42/91 days and the ten never-recalled ones legitimately
overdue. Decision (the user's): switch the unit to the problem, migrate by
replaying the attempt log, **spread** the overdue never-recalled backlog over a
week, keep the daily budget small (2 in `dojo day`, `--limit N` for
`dojo warmup`) and surface what is still waiting. `pattern_cards` stays as a
legacy table; `dojo rebuild-cards` re-derives cards from history (the repair
path). See docs/retention.md for the model and the replay's one honest limit
(eight pre-v0.11 recalls lost their grade and replay as "good").

**Stage D (roles + providers).** The backend protocol takes a `Role`
(`chat(role, system, user)`), so routing is an argument instead of a guess:
`MockBackend` keys its canned answers on the role, the live backends use it for
the system prompt's address, the budget and the request's provenance. That
retires the old substring convention, which had let a *test fixture dictate
product copy* (`TEACHER_SYSTEM` had to avoid the words "tutor"/"discussion") and
had silently mis-routed the discussion branch once. The provider table adds
OpenAI (same wire as DeepSeek, different host/model/key) and Anthropic (top-level
`system`, `max_tokens`, no `response_format` — JSON comes back through a forced
`emit_json` tool call, with the tolerant parser behind it); `DOJO_MODEL` and
`DOJO_MODEL_<ROLE>` choose models, per-role budgets make the every-hint audit
cheap, `dojo setup` detects any provider's key and records `DOJO_PROVIDER`, and
`attempts.ai_provenance` records what produced each review. `tests/test_backend.py`
pins request construction for both wire formats against injectable fake clients.

**Found on the way (each now fixed and pinned):** EOF at a prompt (Ctrl-D, a
piped script running out) raised a traceback out of `rich.Console.input` — it now
stops cleanly and says the session is resumable; `_fast_probe` never actually
shrank the ladder (`setdefault` against an explicit kwarg), so every flow test ran
the full 7-size probe; `FakeConsole` silently answered "quit" when a script ran
out, which had been hiding three under-specified tests; a template with no stored
signature rendered `def name:`, which does not compile.

## Stage 0 — the trust fixes this stage depends on

These are audit findings S1.1, S1.2, S1.3, S1.5, S2.5, S2.17. They are one
day's work and they must land **first**, because v0.13 adds AI call sites
(Stage C switches what four prompts receive) and code paths (`submit` inside the
post-solve phase) that would otherwise inherit them:

1. `tutor._audit` fails **closed**: a non-JSON / missing / non-int rating
   discards the hint and prints "couldn't verify that one — try rephrasing".
   One test per failure mode.
2. `judge.runner` captures the child's **file descriptor 1** (dup2 onto a temp
   file) alongside `sys.stdout`, and the parent's `json.loads` is wrapped: a
   malformed protocol becomes `status="error"` with the offending text, never an
   exception out of `run_cases`.
3. `run_cases` refuses empty case lists, and `_submit` refuses a problem whose
   *parsed* `visible_tests` is empty (not just falsy as a string).
4. `cli.main` wraps dispatch in a boundary that turns an ESC/transport error into
   "‹agent› unavailable — carrying on" and keeps the session alive.
5. Case-level exceptions produce `status="error"`, and `expected` is read inside
   the per-case `try`.
6. **Unpin the flake**: `tests/test_flow.py:1187` asserts a class from real
   timings (33% failure at 6-way concurrency). Pin the *verdict plumbing* on
   synthetic ratios and assert only that a verdict was produced end-to-end.
   Same for `tests/test_probe.py:242-254`.
7. **Replace the never-solve guard grep with a real boundary check**
   (`tests/test_never_solve.py` asserts five literal strings are absent from
   tutor sources — it stays green if a solution is passed as the `statement`
   argument, or arrives via a transitive import). Stage C changes what the tutor
   receives, so the guard should be an import-graph assertion plus a provenance
   check at the call site *before* that change lands.

## Stage A — attempt revisions (report #1: the original submission survives)

**Spec.** Every write of `attempts.code` also appends an immutable revision row
in the same transaction.

```sql
CREATE TABLE IF NOT EXISTS attempt_revisions (
    id                 INTEGER PRIMARY KEY,
    attempt_id         INTEGER NOT NULL REFERENCES attempts(id),
    revision           INTEGER NOT NULL,   -- 1-based, per attempt
    kind               TEXT NOT NULL,      -- 'submit' | 'polish'
    code               TEXT NOT NULL,
    status             TEXT NOT NULL,      -- the judge's verdict at this revision
    judge              TEXT,               -- JSON: totals + per-case failures
    self_reported_time TEXT, self_reported_space TEXT,
    measurement        TEXT,               -- JSON probe record for THIS revision
    static_analysis    TEXT,
    review             TEXT,               -- the review as of this revision, if any
    reflection         TEXT,
    created_at         TEXT NOT NULL,
    UNIQUE (attempt_id, revision)
);
```

`attempts` keeps `code`/`review`/`measurement` pointing at the newest revision
(every existing query and `dojo show` default keeps working); `polished` stays as
a denormalized counter for compatibility. Each revision carries the artifacts
*its* code produced, which also fixes S2.4 (a failed re-review currently wipes
the existing review) for free: the previous revision still has its review.

**CLI.**
- `dojo show <id> --revisions` — one row per revision: n, kind, status,
  claimed/measured complexity, review overall, timestamp.
- `dojo show <id> --rev N` (repeatable, `--rev all`) — that revision's code,
  claims, measurement, review, static analysis.
- `dojo show <id> --diff [N [M]]` — unified diff between consecutive revisions
  (or two named ones). This is the feature that makes the row *useful*: "your
  polished version is 12 lines shorter and one class better".
- `dojo show <id>` unchanged, plus one dim line: `3 revisions — dojo show 42 --revisions`.

**Files.** `db.py` (DDL + `attempt_revisions` helpers + `insert_revision`),
`session/flow.py` (`_record_submit`, `_polish` → one `_persist_revision`),
`cli.py` (`_cmd_show` flags, `_cmd_history` a `revs` column), `docs/architecture.md`.

**Tests.** A session that fails once, passes, then polishes stores 3 revisions
with distinct code and the head equal to the newest; revision 1's review is
still readable after a re-review; `--diff` renders; a crash between the head
update and the revision insert cannot happen (single transaction) — pin that
with a forced exception mid-write.

**Risk.** Disk growth (one code blob per revision; irrelevant at this scale).
Compatibility: `attempts.code` remains the head, so no migration of old rows is
needed and pre-v0.13 attempts simply have no revisions.

## Stage B — one loop, two phases (report #2: `check`/`open`, and what `polish` means)

**Spec.** Replace `run_day`'s pre-submit `while True` and `_post_solve_loop`
with one dispatcher over an explicit state:

```
phase: solving | post_solve        # which commands are enabled
agent: tutor   | discussion        # who answers a question
```

| Command | solving, agent=tutor | solving, agent=discussion (after `polish`) | post_solve |
|---|---|---|---|
| `open` / `check` | ✓ | ✓ | ✓ |
| `submit` | judge; on pass → post_solve | re-judge, append a revision, → post_solve | — (say "use `polish`") |
| `polish` | — | — | → solving, agent stays discussion |
| `review` | — | ✓ (re-run the reviewer on the current code) | ✓ |
| `learn` / `report` | ✓ | ✓ | — |
| `quit` | abandon (records nothing) | **keep the attempt**, end the session | same |
| `done` | — | — | end the session |
| anything else | question → tutor | question → discussion | question → discussion |

The agent is sticky by design: once a solve has been graded, the boundary is
lifted and cannot un-lift — so a question asked while polishing gets a real
answer (with code, if useful), which is exactly why you polish. Every question
prompt still carries the *current file contents* (`build_discussion_prompt`
already does), so the model grounds on what the student is editing right now.

The `review` command absorbs the old `Review again? [y/N]` prompt (which stays as
the default after a re-submit, since re-grading without re-reviewing is a strange
default).

**Files.** `session/flow.py` (one loop, a `COMMANDS` table, `post_solve`/`polish`
handlers), `session/state.py` (persist `phase`/`agent` so a crash mid-polish
resumes in the right mode — with unknown-key tolerance, which is already there),
`terminal.confirm_typo` command lists per phase, hints per phase
(`COMMANDS_HINT`/`POST_COMMANDS_HINT` become one table-driven string).

**Tests (rule 6 — the mock and these move together).** `check` in post_solve runs
the visible tests; `open` in post_solve launches the editor; `polish` switches
phase and a subsequent question reaches the **discussion** agent; `submit` while
polishing appends a revision and does not create a second attempt; `quit` while
polishing keeps the attempt row; the typo guard offers the phase's own commands;
no input can reach the AI that was meant as a command (the reproduced bug today:
`check` and `open` are sent to the model).

**Risk.** This replaces the most test-covered part of the app (the flow tests).
Do it as one commit with the phase table, not incrementally — half a dispatcher
is worse than either.

## Stage C — the workbench file, and the runnable entry point (reports #3/#4, feature #1)

**Spec.** A new module owns the artifact and its views:

```python
# src/dojo/session/workbench.py
render_template(problem)   -> str      # shebang + statement + stub + example block
student_view(source, problem) -> str   # chrome stripped: what the AI should judge
is_pristine(source, problem) -> bool   # untouched template? (warn, never grade)
example_block(problem) -> str          # sentinel-fenced __main__, or "" if not expressible
```

The template gains a fenced, auto-generated examples block:

```python
# --- dojo: visible examples (auto-generated — run this file, or press F5) ---
if __name__ == "__main__":
    _cases = [(([2, 7, 11, 15], 9), [0, 1]), (([3, 2, 4], 6), [1, 2])]
    for _i, (_args, _want) in enumerate(_cases, 1):
        _got = two_sum(*_args)
        _ok = _got == _want
        print(f"case {_i}: got {_got!r}  want {_want!r}  {'ok' if _ok else 'FAIL'}")
# --- end dojo ---
```

Details that matter:

- **Guarded, so grading is unaffected.** Both the judge (`spec_from_file_location("solution", …)`,
  `runner.py:66`) and the probe (`"measured"`, `probe.py:99`) load the module
  under a name that is not `__main__`, so the block never runs during `check`,
  `submit`, or the scale probe — verified by execution. The reverse is a small
  teaching win: a student who writes a bare top-level call now has a *guarded*
  example in front of them.
- **Built from the problem's own visible tests** (`visible_tests` is already
  data), so the block never disagrees with `check`. Cases whose comparison mode
  is `sorted`/`approx`/`predicate` get the matching inline comparison and a
  `# compare: sorted` comment; `ops` cases get the class-driver replay the
  harness already implements. A case that is not literal-expressible is skipped
  with a comment rather than emitted broken.
- **Sentinel-fenced**, so `student_view()` removes it byte-exactly and a re-render
  can replace it without duplicating.
- **The statement docstring is stripped only when it equals the problem
  statement** — if the student rewrote it, it is their code and stays.
- **`static.analyze` runs on the student view** (write it to a temp file), so
  dojo's chrome can never generate a finding, and the `.ruff_cache` write moves
  to dojo's data dir.

Every AI reader switches to `student_view`: the tutor (`do_hint`), the reviewer
(`_submit`/`_polish`), and the discussion prompt. `REVIEWER_SYSTEM` also gains one
honest sentence — *dojo scaffolds the shebang, the statement docstring, and the
examples block; the submitted view omits them, so do not critique their absence* —
as belt-and-braces against the model inferring them from the statement. This is
the structural half of the fix; the prompt line is the cheap half, and the two
together retire the class of noise seen in 15 of 18 live reviews — including the
review that cited a ruff `EXE001` finding dojo's ruff configuration cannot emit
(audit S4.3).

`dojo show`'s code panel gains `--clean` to display the student view; the stored
`code` stays the raw artifact (the truth of what ran).

**Files.** new `session/workbench.py`; `session/flow.py` (template write, all four
prompt call sites, `_check`), `static.py` (source-instead-of-path entry point),
`tutor/prompts.py` (+ mock + `tests/test_reviewer.py`,
`tests/test_prompt_routing.py`), `cli.py` (`show --clean`), `editor.py`
(unchanged — `${file}`/`$ZED_FILE` already point at the right file),
`docs/architecture.md`, `README.md`.

**Tests.** `student_view(render_template(p), p)` removes the shebang, the
statement, and exactly the fenced block, and is idempotent; a template whose
statement contains `"""`, a trailing quote, or a backslash **still compiles**
(audit S2.7 — validate the rendered template with `compile()` before writing);
the examples block runs under `python <file>` and prints one line per case, and
`python <file>` on the untouched stub prints `NotImplementedError` rather than
nothing; the judge and probe import path never executes the block (assert via a
module-level side-effect counter); the reviewer prompt contains no shebang and no
statement-docstring duplication.

**Risk.** The statement docstring is also what `bank.parse_problem_file` reads for
the *seed corpus* — that is a different artifact (the problem file, not the
workbench file) and is untouched. Do not let the two paths share a code path
"for symmetry"; they have different contracts.

**Why not the separate-runner-file design (option B).** It is defensible — the
workbench file stays pristine and the runner can add a timeout — but it needs
import-by-path (slugs contain `-`, so `import` is out), a second generated file
to keep in sync, and IDE config whose `program` must be an absolute path (the
current configs use `${file}`, which is right for the file you are editing).
Its cleanliness advantage mostly evaporates once `student_view` exists, while its
failure modes are permanent. If the block ever becomes intolerable, option B is a
strict superset of the plumbing that already exists — but it is not the first
move.

## Stage D — providers: OpenAI, Claude, and roles (feature #2)

**Spec.** A provider table in `config.py`:

```python
PROVIDERS = {
  "deepseek":  Provider(base_url="https://api.deepseek.com", model="deepseek-chat",
                        key_env="DEEPSEEK_API_KEY", json_mode="object"),
  "openai":    Provider(base_url=None, model="gpt-4.1-mini",
                        key_env="OPENAI_API_KEY", json_mode="object"),
  "anthropic": Provider(base_url=None, model="claude-sonnet-4-5",
                        key_env="ANTHROPIC_API_KEY", json_mode="tool",   # no response_format
                        system_field="system"),
}
```

- `DOJO_PROVIDER` selects one (default `deepseek`, `mock` still available);
  `DOJO_MODEL` overrides the model; `DOJO_MODEL_<ROLE>` overrides per role.
- `get_backend()` constructs `OpenAICompatBackend` (base_url differs only for
  DeepSeek) or `AnthropicBackend` (new `anthropic` dependency; system prompt as a
  top-level field; JSON via a forced tool call, falling back to the tolerant
  parser + the existing retry path).
- **Roles on the protocol.** `chat(role, system, user)` / `chat_json(role, …)`
  with `role ∈ {tutor, discussion, teacher, reviewer, auditor, curator, auditor_curation, referencer}`.
  This retires MockBackend's substring routing — which currently *constrains
  product copy*: `TEACHER_SYSTEM` may not contain the words "tutor" or
  "discussion" (AGENTS.md; the branch has silently died once), and
  `tests/test_prompt_routing.py` exists only to police that.
- **Per-role budgets**: the leak audit needs ~64 output tokens and no JSON mode
  syntax beyond `{"rating": …}`; the review needs 4096; the tutor 2048. Per-role
  `temperature`/`max_tokens` make the audit cheap and fast on every provider.
- **The setup wizard** detects all three keys, asks which to use when more than
  one is present, writes `DOJO_PROVIDER` to `.env`, and the "no key" error names
  every accepted variable. `dojo setup --provider X` for scripted installs.
- **Provenance**: the debug log records provider+model per event, and (audit
  S3.1) the attempt row stores `ai_provenance` JSON (provider, model, prompt
  version) — so a mock row can never be mistaken for a live one again.

**Files.** `config.py`, `tutor/backend.py` (backend classes + roles + retry),
`tutor/tutor.py` + `reviewer.py` + `session/flow.py` + `session/learn.py` +
`curator/curator.py` (call sites pass a role), `setup.py`, `db.py` +
`migrations` (additive `attempts.ai_provenance`), `docs/architecture.md`,
`README.md`, the mock and `tests/test_prompt_routing.py` (rule 6).

**Tests.** Per-provider fake clients (no network) asserting: the system prompt
lands in `messages[0]` for OpenAI-compatible and in the top-level `system` field
for Anthropic; `response_format` is sent only where supported; the forced-tool
JSON path parses through the same normalizers; role routing is exact (no
substring matching — delete the escape hatch at `tests/test_flow.py:435`);
per-role `max_tokens`; `get_backend()` errors mention all three key variables;
the wizard's detection order; `ai_provenance` is written for every attempt.

**Risk.** Behavioral differences across providers are the point, so *prompts*
will need per-provider tuning: budget one prompt-review pass after the switch,
and keep `prompt version` in the provenance record so score trends can be read
per instrument. Also: the audit's fail-closed change (Stage 0) interacts here —
an audit call that fails on a provider quirk must discard the hint, not deliver
it.

## Definition of done

- The four reported defects are gone, each pinned by a test that fails before the
  change: a polished attempt keeps both versions; `check`/`open` work after
  submit; `polish` returns to solving with the discussion agent; no AI prompt
  contains dojo's shebang, statement docstring, or examples block.
- `python ~/.local/share/dojo/workbench/<slug>.py` prints one line per visible
  example, and the untouched stub prints a `NotImplementedError` traceback —
  i.e. "Run" and "Debug" in the IDE do something on every problem.
- `DOJO_PROVIDER=openai` and `DOJO_PROVIDER=anthropic` complete a full mock-free
  session end to end (one manual pass each, not in CI).
- `uv run pytest` green, offline, and no test asserts a class from wall-clock
  timing.
- README (the daily loop, the provider section, the debugging story), AGENTS.md
  (session phases, the workbench view layer, the backend protocol), and
  `docs/architecture.md` updated in the same commits.
